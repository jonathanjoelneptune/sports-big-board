# Sports Big Board v6.0.0 — Canonical Event / Slate Shadow

## Purpose

v6.0 introduces the Canonical Event Schema as a **parallel shadow database**. It does not replace Day State, the ribbon, score authority, Game Center, or media discovery in this release.

The shadow system exists to prove that a future canonical slate can account for every event Sports Big Board intends to show before it is granted production authority. v6.0 also adds a separate direct ESPN discovery path for the seven initial leagues so the comparison is not merely a replay of Day State/history.

## Initial competition scope

- MLB
- NFL
- NBA
- NHL
- EPL
- MLS
- NCAAF

Dynamic competition/league activation is intentionally deferred until the canonical slate is proven.

## Safety boundary

- Existing Day State remains production authority.
- Existing history/catalog repository remains untouched.
- Canonical data is stored separately at `~/.sports-big-board/canonical-shadow-v6.sqlite3` by default.
- A provider/event disappearing from a later observation never deletes the canonical event.
- v6.0 cannot mark a slate `CERTIFIED` from Day State + history-catalog evidence alone because both descend from the current production architecture.
- Direct ESPN collection is classified as `DIRECT`: it counts as shadow discovery, but cannot certify a slate by itself because ESPN is also used elsewhere in Sports Big Board.
- Certification requires every included event to have both `AUTHORITATIVE` and `INDEPENDENT` evidence and zero unresolved identity/inclusion conflicts.

## Canonical database

Tables:

- `canonical_event`
- `provider_event_mapping`
- `schedule_observation`
- `source_coverage`
- `score_observation`
- `daily_slate`
- `daily_slate_event`
- `slate_comparison`
- `shadow_run`

The store uses SQLite WAL and is append/update biased. Event disappearance is never inferred from source absence.

## Identity resolution

Resolution priority:

1. previously known provider-event mapping
2. same competition/date/participants + explicit event sequence
3. same competition/date/participants + compatible scheduled time and no same-provider ID conflict
4. otherwise create a separate event with `UNRESOLVED_PAIR_COLLISION`

This deliberately fails open into an unresolved second event rather than silently combining a possible doubleheader.

## Schedule and score observations

Every observed event writes:

- source and source class
- participant identity
- scheduled time
- status
- venue / game sequence where available
- provider IDs
- score/status/period/clock state
- first/last observation timestamps

Identical observations are deduplicated while their `last_observed_at` and observation count continue to advance.

Every completed provider query also writes `source_coverage` for each league/date, including successful zero-event results. This is necessary because per-event evidence cannot prove that a no-game day was actually checked.

## Daily slates

The worker maintains D-7 through D+7 by default.

- full horizon reconciliation: every 15 minutes by default
- current-day hot reconciliation: every 60 seconds by default
- 2:00 AM America/New_York is a prioritized daily baseline boundary; the persisted baseline survives backend restarts without duplicating the baseline version
- material event membership, inclusion, scheduled-time, postponement, or cancellation changes create a new immutable slate version
- LIVE/FINAL score transitions are recorded in `score_observation` and do **not** churn slate versions

Slate states:

- `SHADOW_BASELINE` — legacy evidence captured, independent proof not complete
- `RECONCILING` — identity or inclusion-policy issue exists
- `CERTIFIED` — authoritative + independent **date coverage** exists, every included event has authoritative + independent event evidence, and no identity/inclusion conflicts remain. A true zero-event day can therefore be certified rather than merely inferred.

## NCAAF

MLB/NFL/NBA/NHL/EPL/MLS catalog events are included under `ALL_LEAGUE_EVENTS`.

Historical `CFB`/college-football league aliases are normalized to canonical `NCAAF` before ingestion.

NCAAF is deliberately different:

- an NCAAF event observed in production Day State is `INCLUDED / LEGACY_BOARD_POLICY`
- a catalog-only NCAAF event is `UNKNOWN / NCAAF_POLICY_PENDING`

This prevents v6.0 from incorrectly assuming the full college-football universe belongs on the ribbon before the explicit Top-25/featured-game policy is moved into the canonical layer.

## Direct shadow discovery

The v6.0 worker directly queries ESPN scoreboards for MLB, NFL, NBA, NHL, EPL, MLS and NCAAF. The D-7/D+7 full-horizon pass uses one ranged scoreboard request per league; today's hot pass refreshes each league separately. These observations are stored as `ESPN_DIRECT / DIRECT`.

This path is intentionally independent from the *current processing pipeline*, even though ESPN itself is not an independent certification authority. It can therefore expose a Sports Big Board ingestion/discovery bug such as a game that ESPN knows about but production Day State omitted.

For NCAAF, a direct event with positive ESPN Top-25 rank evidence can be included as `DIRECT_ESPN_TOP25`. A direct event without positive Top-25 proof remains `UNKNOWN`; it is not silently excluded, because future/past ranking applicability must be proven separately.

## Shadow comparison

For any Day State snapshot, the system compares **new shadow discovery evidence** (`DIRECT`, `AUTHORITATIVE`, or `INDEPENDENT`) against production Day State. Legacy observations are still retained in a **safety union**, but they do not count as a shadow discovery. This is important because otherwise a production-only miss could never be visible.

The comparison records:

- shadow-discovered count
- production count
- matched count
- shadow-only events
- production-only events
- safety-union count / legacy-fallback-only events
- first/last time that comparison state was observed

A production-only event is a cutover blocker. A shadow-only event is evidence that v6.0 may be protecting a production omission.

## Shadow validation frontend

Open `canonical-shadow.html` on the deployed Sports Big Board host. It is a read-only D-7/D+7 comparison console showing canonical/legacy totals, certification states, and canonical-only or legacy-only discrepancies by league and day. It refreshes once per minute and does not alter production state.

## Next canonical-slate step

v6.0 now includes the direct discovery collector. The next v6.x increment should add the **certification sources**: league/official schedule adapters where available plus a genuinely independent corroborating schedule source, then call:

`CanonicalShadowEngine.observe_external_event(event, league, slate_date, source, source_class)`

with `source_class=AUTHORITATIVE` or `INDEPENDENT`.

That lets the exact same shadow database progress from `SHADOW_BASELINE`/`RECONCILING` to genuine `CERTIFIED` slates without changing the Big Board frontend or the production Day State path. No production cutover should occur until the live shadow window has zero unexplained production-only events and the intended leagues meet the certification gates.


## Applying the v6.0 overlay

The release package is an overlay, not a stale full-repository copy. Extract it at the root of the current Sports Big Board 5.5.0 checkout, then run:

```bash
bash APPLY-V6.sh
```

`tools/apply_v600_release.py` atomically:

1. appends the canonical installer to the existing `sbb/__init__.py` instead of replacing it,
2. extends the existing `VERIFY.sh` instead of replacing it,
3. synchronizes active semantic release references from 5.5.0 to 6.0.0,
4. leaves historical packaged-version directories untouched, and
5. runs the repository release-integrity checker before `VERIFY.sh` executes.

The GitHub integration available in this ChatGPT session is read-only for branch creation, so the release is packaged for application to the live checkout rather than silently committed to `main`.
